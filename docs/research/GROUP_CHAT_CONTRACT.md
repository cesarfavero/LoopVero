## Recovered renderer contract

`NewChatBar` is exported from `chunk-new-chat-bar-BqaDAl0q.js`. Its parent supplies agents, selected recipients, group mode, creation-pending state, team agents and callbacks for recipient changes, group mode, team-bot creation, commit and close. The component is not a plain text field: it renders recipient chips and a combobox/listbox with keyboard navigation, highlighted options, loading state, localized empty states and virtualized rows. The list has ARIA combobox/option relationships and the root reports `aria-busy` during creation.

Recipient selection is differentiated by kind (`agent`, `human`, or a new/provisional agent). Enter, Tab, comma, Backspace, Escape and arrow keys have explicit branches. The component treats normal recipient selection, the team-agent picker and group-mode entry as separate paths. It receives the current group chat and team data to calculate valid candidates. Those details come from the module AST and readable code, not a design mock or screenshot.

The parent state machine is in `index.eager-app-DSuGVQNC.js`. Its `wze` transaction checks recipient and send-draft preconditions; starts a group creation intent; associates the current composer draft; creates provisional recipient agents when required; and calls `roster.createGroup` with `name`, `description`, `memberAgentIds`, and optional `humanMemberUserIds`. It cleans up provisional agents on abandonment and selected failures. On success it attaches the returned group agent to the creation intent, migrates or clears/restores the draft as appropriate, optionally sends the first message, and selects the created group. On errors it reports failure, attempts provisional cleanup, recovers the draft and records retryability according to the failure boundary.

The roster wrapper calls the underlying `createGroup` operation and ingests the returned group into local roster state. It refreshes the roster when the created group uses the Temporal harness. `setGroupMembers` similarly calls the underlying operation and refreshes for Temporal groups. These are static call paths; whether any gate is enabled in a live account is not established by the bundle alone. The observed feature gate name in renderer code is `grok_bot_multiplayer`; separate team/feature checks also constrain which options appear.

The local Sand Host group configuration uses `sand-group.json` with a version and member IDs, and roster emission follows creation. `setGroupMembers` validates and persists a new non-empty member list under corresponding constraints.

This establishes a group entity in the supplied host harness code. ## Reconstruction implications

The current `apps/desktop` data model stores individual bots and cannot represent group members, human recipients, provisional-agent cleanup, group draft migration or roster refresh. A faithful implementation therefore requires a first-class group/room contract across persistence, coordinator, renderer and transcript before adding a group UI. The model must retain recipient kinds and the original creation/send/draft states; reducing the feature to a visual multi-select over independent bots would not preserve the observed lifecycle.

The current app also does not implement the original renderer shell or its navigation/state graph. This contract covers the group composer and creation lifecycle only; it is not evidence of complete UI parity. The CodexRouter global service/configuration is outside the replica and must not be changed. Any replica provider integration remains scoped to this app's local configuration.

## Creation transaction: exact compiled handler

The `wze` function in `index.eager-app-DSuGVQNC.js` (byte offsets 1,073,463–1,075,454) is the handler used by the group creation path. Direct AST-range extraction of the shipped bytes corroborates the previously documented lifecycle:

1. It returns without creating anything when there are no recipients, or when the intent is `send` and both prompt and attachment list are empty.
2. It refuses to start while another creation has no outcome, and also blocks a group creation whose previous failure has no retry command.
3. It begins a `group` creation intent and associates the source slot draft before recipient provisioning.
4. Existing agent IDs and human user IDs are accumulated separately. A provisional/new recipient is created through `roster.createAgent` with the `box` creation route and `IC` harness; created IDs are tracked for cleanup.
5. If the intent is abandoned, provisional agents are deleted when the account is still current. Otherwise, `roster.createGroup` receives the name, empty description, agent IDs, and human IDs only when present.
6. Failure is reported and mapped to a retryable group command only for the specific recognized failure code. Provisional cleanup is attempted on pre-create or that retryable failure; refused/failed cleanup changes the failure to a non-retryable cleanup error. The draft is recovered and the creation intent is failed.
7. On success, the returned group agent becomes the creation intent's agent ID. The original draft is cleared only if its identity is still current. `draft` intent restores the draft under the new group; `send` intent records first-message sending and dispatches the draft, then selects the group.

This exact handler confirms important ordering and failure boundaries that a replica must preserve. It does not itself establish which visible button or route invokes it, the runtime feature gate, the remote server behavior, or transcript rendering. Those remain separate mappings. The user's implementation stays independent in `apps/desktop/`; this evidence does not justify a UI-only multi-select.

## Sand Host room routing and transcript turn loop

The extracted `host-main.cjs` has two room creation paths. Its standard `createGroup` resolves requested members against current agents, rejects nested groups, requires at least one existing member, caps the deduplicated set, creates a local agent, stores `sand-group.json`, and emits the roster (`host-main.cjs:738416-738459`). The `server-agent-proxy` separately caches `serverRoomsEnabled` from `GetGrokBotRuntimeCapabilities`; the capability cache is bounded by a TTL. `createRoom` ensures non-Temporal members are mirrored/server-created, generates the room agent ID client-side, calls `CreateGrokBotRoom` with retry policy, checks the returned ID exactly matches, adopts the confirmed server agent and refreshes roster. If the server turns the feature off during creation, it returns a refusal/retry marker rather than blindly creating another room (`714722-714860`).

The host's group-turn manager selects a Temporal member turn only when the member's harness is Temporal. It resolves room members, removes the current member from peers, records work state, requests the delegated turn and maps the result to shown/not-shown/stopped. The temporal member adapter serializes up to the last 24 messages with bounded speaker/content/reply-quote fields, sends room/member/peers/new messages/winding-down/deadline, and registers a pending nonce before the RPC. Accepted and duplicate dispatches wait for the return result; non-Temporal/not-found dispatches skip; unavailable/unspecified dispatches become errors. Results must match both pending nonce and room ID. Delivered structured posts are decoded, degraded/unknown forms are reported, and empty text posts are removed. A host deadline settles the pending turn as timeout and issues best-effort upstream cancellation; room cancellation settles all matching pending turns.

The Coordinator's generated service descriptor at `main.cjs` offsets 576,159–576,527 exposes the room-member request, cancel, deliver-result, create-room and set-members RPC schemas. A focused REA pass over Coordinator and proto (Evidence `ev_9da8ff71686b41bc6eda794877545b6c9fe6d6a59dc7161dc6eb5721d2c06e90`) parsed both files without syntax failures but retained partial semantics. Static scan found no Coordinator invocation sites for those camel-case room-member RPC methods; its `createGroup` command route is a separate generic control-client path. This does not contradict the host-side backend client calls and does not prove absence from the backend or dynamically bound service code.

This closes a source-level host route from a group turn through the authenticated backend client and back to transcript orchestration. It does not prove a live account's capability flag, backend execution, or exact mapping from resulting posts to renderer rows.
